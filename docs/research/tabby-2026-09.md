# Tabby research: long context, prefix reuse, concurrency, tool calling, and SSD caching for the SwarmLLM WebGPU engine

Researched 2026-09-26. Engine context: Qwen 3.8 27B hybrid (48 Gated-DeltaNet + 16 full-attention layers, 24q/4kv heads, head dim 256), Q4_0/Q8_0 weights, native MTP, layer-split over WebRTC.

Network note: this sandbox's egress proxy blocked x.com, fxtwitter, nitter, arxiv.org, huggingface.co, lmsys.org and pytorch.org. GitHub pages were readable. Everything else comes from web-search snippets, and those claims are marked as coming from search.

## 0. Sizes for our model (derived from engine/qwen35.js dims)

| Item | Per token / per snapshot | 8K | 32K | 64K |
|---|---|---|---|---|
| Full-attn KV, f32 (16 layers x 4 kv x 256 x K+V) | 131 KB/token | 1.07 GB | 4.3 GB | 8.6 GB |
| KV f16 | 65.5 KB/token | 0.54 GB | 2.1 GB | 4.3 GB |
| KV q8_0 (8.5 bit) | ~35 KB/token | 0.28 GB | 1.1 GB | 2.3 GB |
| KV q4_0 (4.5 bit) | ~18 KB/token | 0.15 GB | 0.6 GB | 1.2 GB |
| DeltaNet state snapshot (48 layers x 48 v-heads x 128x128, plus conv 3x10240 per layer), f32 | ~150 MiB total, **independent of length** | | | |

These totals are for the whole model. With a layer split each device holds only its own share, for example about 1/4 each on 4 devices. The KV cache is small at 8K. At 32K–64K it dominates unless it is f16 or q8. The DeltaNet (DN) snapshot is a fixed ~150 MiB, or ~75 MiB in f16, so we can afford a few checkpoints per session but not one every 64 tokens.

Repo state when this was written: `tabby-kernel` adds an f16 KV cache + split-K flash decoding (`attn_flash` / `attn_combine`), session state export/import, and 8192-token rooms for the 27B; see docs/tabby-kernel.md. `room/conversation.js::fitContext` still drops old turns (breaks prefix reuse, see 3).

### 1a. @SamuelZengML/status/2097861839287927139 (2026-09-10 01:36 UTC)
A web search for the status ID returns the post itself plus press coverage. **Samuel Zeng (Audio8.ai) is announcing the open-source release of Edge0.** It runs a 35B MoE (Qwen3.5-MoE 35B-A3B base, 4-bit) on an iPhone with 1–2.5 GB peak memory. The method is to **stream MoE experts from flash storage on demand**, with two additions:
- A trained **"prerouter"** that predicts the next step's experts, so loads overlap with compute. They claim up to +59% decode throughput.
- A **Recover-LoRA** adapter that recovers quality after quantization and streaming. They report an average loss of 3.9 points versus FP16 for the 35B.

Reported speed is 14.9–17.7 tok/s on a Mac mini M4 Pro. The MLX backend is available now and a CUDA backend is planned. Sources: [Edge0 repo](https://github.com/Edge0-AI/edge0), [HF model](https://huggingface.co/Edge0/Edge0-35B-A3B-preview), [runtimewire](https://runtimewire.com/article/edge0-open-source-35b-model-streaming-inference), [MindStudio](https://www.mindstudio.ai/blog/edge0-35b-phone-memory-moe), related paper ["The Other Half of the Memory Wall" arXiv 2609.18063](https://arxiv.org/pdf/2609.18063).

**Applies to us?** Mostly **no**. Qwen 3.8 27B is dense, so every weight is touched on every token, and streaming weights from SSD would limit decode to disk bandwidth. Our answer to memory limits is already the layer split across peers. Two parts do transfer:
- **Predict the next unit of work and prefetch it while computing.** For us that means prefetching KV/DN snapshots from OPFS while earlier stages run.
- **If a future Tabby model is an MoE,** expert streaming plus a prerouter is the way to fit it on phones.

## 2. Swarm and distributed engines, and what they do that we don't

### Mesh-LLM ([Mesh-LLM/mesh-llm](https://github.com/Mesh-LLM/mesh-llm), Rust + iroh/QUIC + llama.cpp "Skippy")
This is the most relevant project by far. It is a distributed llama.cpp mesh with an OpenAI-compatible API. There are also unrelated forks and namesakes, such as [IvGolovach/mesh-llm](https://github.com/IvGolovach/mesh-llm), a llama.cpp reference implementation.

- **Model split:**
  - Dense models are split into contiguous layer "stages". The coordinator starts downstream stages first and then publishes the stage-0 route. It uses a latency-aware topology planner.
  - For MoE, each node gets an overlapping expert shard (shared core plus unique experts), so there is *zero* cross-node traffic.
  - The activation wire is **raw f32**. The docs say f16/q8 activation compression attempts "failed" and remain research ([SKIPPY_SPLITS.md](https://github.com/Mesh-LLM/mesh-llm/blob/main/docs/SKIPPY_SPLITS.md)). Our f16 wire with a NaN/overflow guard is ahead here.
- **KV:** Q4_0 K/V cache on the large "Inkling" model, with `--ctx-size 131072` offered but "not a completed 128K workload proof".
- **Prefix cache** ([PROMPT_CACHE.md](https://github.com/Mesh-LLM/mesh-llm/blob/main/docs/skippy/PROMPT_CACHE.md)):
  - Three tiers: L1 in-process radix, L2 host RAM, L3 disk.
  - Exact-prefix identity plus a "shared-prefix grid" at a configured stride.
  - **For hybrid/recurrent families it stores an indivisible "exact-state snapshot" including recurrent + conv buffers.**
  - L2 promotion happens on a second hit within 10 min, or on the first hit for prefixes of at least 4,096 tokens. Payloads over 64 MiB are excluded from L2.
  - It reports `cached_tokens` OpenAI-style.
- **Disk tier** ([KV_CACHE_DISK.md](https://github.com/Mesh-LLM/mesh-llm/blob/main/docs/skippy/KV_CACHE_DISK.md)):
  - BLAKE3 content-addressed segments plus a manifest. A manifest is loadable only when all segments are present and the digest matches, so "partial state is unreadable by construction".
  - Corrupt entries are quarantined.
  - Eviction is oldest-manifest-first down to 85% of budget, with an auto budget of min(20% of FS, 64 GiB).
  - Optional CacheGen codec.
- **Speculative decoding across a pipeline** ([PIPELINED_VERIFY_WINDOW.md](https://github.com/Mesh-LLM/mesh-llm/blob/main/docs/skippy/PIPELINED_VERIFY_WINDOW.md)):
  - Native MTP supplies the anchor draft and an n-gram cache extends it.
  - Candidate chunks are sent as **multiple VerifyWindows in flight** (FIFO, window IDs, epochs).
  - On divergence the coordinator commits the matching prefix plus the correction, and every later window in the epoch goes stale. Stale windows complete but are discarded.
  - Recurrent state uses "conservative local trim and bounded MTP re-prime".
  - Pipeline depth was swept over 1–16.
- **Suffix n-gram proposer** ([SUFFIX_NGRAM_PROPOSER.md](https://github.com/Mesh-LLM/mesh-llm/blob/main/docs/skippy/SUFFIX_NGRAM_PROPOSER.md)):
  - Finds the longest exact suffix match (3–64 tokens) anywhere in the request history, prefers recent matches, and copies the continuation. Draft length is capped at 2x the match length.
  - Measured on GLM-4.7 coding-copy workloads: **MTP-only 30.5 tok/s → MTP+suffix 78.1 tok/s (+156%)**. Standalone suffix drafting reached 84.9% acceptance.
  - It is aimed squarely at coding-agent traffic: file re-emission with small edits and tool-output echoes.
- **We lack:** tiered prefix cache with hybrid snapshots, content-addressed disk tier, pipelined multi-window verification, long-suffix drafting.

### exo ([exo-explore/exo](https://github.com/exo-explore/exo))
- MLX backend with pipeline and tensor parallelism, topology-aware auto placement, and RDMA over Thunderbolt 5 (2026).
- No documented KV, prefix or speculative features.
- **Takeaway:** a placement solver driven by live topology. That matches our planner and adds little.

### Petals ([bigscience-workshop/petals](https://github.com/bigscience-workshop/petals), [paper](https://arxiv.org/pdf/2209.01188))
- Servers hold contiguous blocks and keep the per-session attention KV cache server-side.
- **The client keeps a replay log of the inputs it sent to each server.** When a server dies, it replays them to a replacement that hosts the same blocks, and the KV cache is rebuilt transparently.
- Reached about 6 tok/s on 70B across the internet.
- **We lack** session fault tolerance when a tab closes. Per-stage input logs would let a new peer rebuild the stage by batched prefill of the logged activations; our f16 wire is 10 KB/token. Alternatively, reload from that stage's OPFS snapshot.

### prima.cpp ([OpenCPIL/prima.cpp](https://github.com/OpenCPIL/prima.cpp), [arXiv 2504.08791](https://arxiv.org/abs/2504.08791v1))
- llama.cpp-based heterogeneous home clusters.
- **Piped-ring parallelism:** each device holds several non-contiguous layer windows and the token goes around the ring several times. This lets a device prefetch its next window's weights from disk while other devices compute.
- The **Halda** scheduler (ILP-ish) assigns layers and the GPU share from each device's compute, disk speed, RAM and OS.
- About 674 ms/token on 70B.
- **Applies:** Halda's cost model for our planner. The ring only helps when weights spill to disk, which is not our case.

### distributed-llama ([b4rtaz/distributed-llama](https://github.com/b4rtaz/distributed-llama))
- **Tensor parallel** over Ethernet, synchronized with q80-quantized activations.
- Node count is a power of 2 and at most the number of KV heads.
- **Doesn't apply:** tensor parallelism needs a sync per layer, and WebRTC latency makes that prohibitive. The q8 activation sync idea is already covered by our f16 wire.

### llama.cpp RPC ([tools/rpc](https://github.com/ggml-org/llama.cpp/tree/master/tools/rpc))
- Remote backends and a layer split driven from a single host.
- `rpc-server -c` caches tensors on local disk so weights aren't re-sent.
- Backend sampling avoids shipping logits.
- "RPC is for capacity, not speed."
- **Takeaway:** do sampling on the last stage and ship only token IDs, which we already do.

### llama.cpp server prompt cache ([PR #16391](https://github.com/ggml-org/llama.cpp/pull/16391))
- `--cache-ram`: a host-RAM prompt cache acting as extra slots, chosen by prefix similarity.
- `--ctx-checkpoints` (default 32) and `--checkpoint-min-step` (default 8192) are **state checkpoints for SWA and recurrent/hybrid models**.
- `/slots/<id>/save|restore` with `--slot-save-path` gives disk persistence.
- Issues show this is fragile for Qwen3-Next/3.6 hybrids: checkpoints were invalidated and every turn did a full re-prefill ([#24055](https://github.com/ggml-org/llama.cpp/issues/24055), [ik_llama #1762](https://github.com/ikawrakow/ik_llama.cpp/issues/1762)). The workaround was checkpoints every few tokens near the end of the prompt.
- **Lesson:** checkpoint placement must line up exactly with where the *next* request will diverge. That is the end of the last assistant message, before the next user or tool turn.

### WebLLM / MLC ([WebLLM paper](https://arxiv.org/html/2412.15803v2), [XGrammar](https://github.com/mlc-ai/xgrammar))
- Single-device WebGPU with a TVM-compiled PagedKVCache. MLC-LLM has prefix-cache reuse ([PR #2664](https://github.com/mlc-ai/mlc-llm/pull/2664)).
- **XGrammar compiled to WASM** gives JSON Schema and EBNF constrained decoding in the browser with near-zero overhead.
- **Takeaway:** XGrammar-in-WASM as an optional tool-call constrainer.

### SwarmLLM namesakes
- [enapt/SwarmLLM](https://github.com/enapt/SwarmLLM): an unrelated Rust/libp2p layer-pipeline network with an OpenAI and Anthropic API, `max_seq_len_override=32768`, and model-part integrity verification.
- [Nehanth/swarmllm](https://github.com/Nehanth/swarmllm) is this project, which is being renamed.

## 3. KV cache for long context, and prefix caching for hybrid models

### KV quantization
- **llama.cpp `-ctk/-ctv`:**
  - q8_0 costs about +0.002–0.05 perplexity.
  - The asymmetric K=q8_0 / V=q4_0 setup gives mean KLD of 0.0018 ([discussion #23470](https://github.com/ggml-org/llama.cpp/discussions/23470)).
  - llama.cpp now applies a Hadamard ("TurboQuant-inspired") rotation automatically.
- **Qwen 3.6-specific** ([LocalBench](https://localbench.substack.com/p/kv-cache-quantization-benchmark)):
  - q8_0 KL is below 0.04, which is fine.
  - q4_0 KL is 0.09–0.12 overall, but **the damage concentrates in long documents (KL 0.58) and tool calling (0.086)**. Those are exactly Tabby's workloads.
  - **Use f16 by default and q8_0 for 32K+. Avoid q4 K.**
- **KIVI** ([arXiv 2402.02750](https://arxiv.org/abs/2402.02750)): quantize K **per-channel** and V **per-token**, keeping a small full-precision residual window of recent tokens. Near-f16 quality at 2 bits.
- **KVQuant** ([arXiv 2401.18079](https://arxiv.org/abs/2401.18079)): quantize K **pre-RoPE**, which gave 0.82 ppl better at 3-bit. For us, per-channel K scales or a Hadamard rotation of K before q8 are cheap in WGSL.
- **Edge multi-agent persistence** ([arXiv 2603.04428](https://arxiv.org/abs/2603.04428), [code](https://github.com/yshk-mxim/agent-memory)):
  - Per-agent Q4 KV is persisted to disk and restored directly, which cuts TTFT 22–136x at 4K–32K.
  - Perplexity changes by -0.7% to +3%.
  - This is the closest published analogue to "many Tabby sessions on consumer hardware".
- **Applies:** yes. Order of work: 1) f16 (in progress); 2) q8_0-style blocks of 32 with an f16 scale for both K and V, dequantized inside `attn_flash`; 3) optionally a per-channel K scale. Quality check: KL versus the f16 reference on long-document and tool-call prompts, not just perplexity.

### Flash-decoding split-K
- Decode attention at 32K+ with one query token must split along the KV sequence to fill the GPU. Each split computes a partial (max, sum, out) and a combine pass merges them.
- ONNX Runtime WebGPU does exactly this with three shaders (QK^T, split-VX, reduce): 34→41 tok/s at 1K on RTX 2000 Ada ([PR #23808](https://github.com/microsoft/onnxruntime/pull/23808)).
- Our `attn_flash` does one 256-thread workgroup per (split, column, kv-head), with the 6 q-heads of a GQA group sharing each K/V read. That is the right design.
- Tuning notes:
  - Pick the split count so that splits x kvHeads x columns is at least about 2–4x the number of SMs/CUs.
  - Use f16 K/V loads as `vec4<f16>` if `shader-f16` is available, otherwise `unpack2x16float` as now.

### Paged attention
- vLLM PagedAttention and ORT WebGPU PagedAttention ([PR #32277](https://github.com/microsoft/onnxruntime/pull/32277); key trick: derive lengths on the GPU to avoid readbacks).
- **Applies partially.** We don't need vLLM-scale paging, but **concurrent sessions with different lengths** need either:
  - fixed per-session slots of maxSeq (simple, wastes memory), or
  - a block table: 256-token blocks, with a `u32` page index read in `attn_flash` per split. Split = page makes this natural.

  A block table also makes prefix *sharing* between sessions free, for example the same system prompt and tool list.

### Prefix / radix caching for hybrid DeltaNet models (critical)
Full-attention KV is token-addressable, so it can be truncated to any prefix. **The DeltaNet recurrent and conv state cannot be rolled back.** A prefix can only be resumed at a position where a DN snapshot was taken.

- **SGLang MambaRadixCache → Unified Radix Cache** ([LMSYS blog 2026-08-11](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache/), [Qwen3.8 day-0](https://www.lmsys.org/blog/2026-08-12-qwen3-8-day0-support)):
  - One radix tree with a FULL component (KV path reuse) and a MAMBA component (GDN checkpoints).
  - Checkpoints are taken **at prefill chunk boundaries and at regular decode intervals**, every 64-token chunk in the base design.
  - On a hit it restores the nearest checkpoint below the match and recomputes the tail.
  - A shared checkpoint is **copy-on-write** into a private slot before mutation.
  - Separate LRUs for KV and for DN states; DN states can be evicted from any node.
  - The `extra_buffer` mode supports speculative decoding.
- **vLLM** ([tracking #26201](https://github.com/vllm-project/vllm/issues/26201), [PR #36649](https://github.com/vllm-project/vllm/pull/36649)):
  - `mamba_cache_mode=align` (the default for Qwen3.5) caches state only at block boundaries. The mamba block is large (e.g. 528/2176 tokens), so short prompts never hit ([#40696](https://github.com/vllm-project/vllm/issues/40696)).
  - `all` mode caches GDN state per block.
  - MTP + prefix cache in `all` mode is recent work ([PR #50172](https://github.com/vllm-project/vllm/pull/50172)).
- **Tail-Replay** ([arXiv 2608.30310](https://arxiv.org/abs/2608.30310)):
  - Keep exact KV and **no** DN checkpoints. On a hit, rebuild DN state approximately by replaying only the last 5–10% of the matched prefix, relying on gated-delta decay.
  - Retains 92.8–99.9% of full-prefill quality on LongBench/RULER.
  - It is lossy, so use it only as a fallback when no snapshot exists. SGLang has an RFC for budgeted tail replay ([#40865](https://github.com/sgl-project/sglang/issues/40865)).
- **Coding-agent traffic** ([TraceLab, arXiv 2606.30560](https://arxiv.org/abs/2606.30560)): 95.7% of input tokens hit the prefix cache across about 350K Claude Code/Codex steps. Contexts are long and outputs short. **Prefix reuse is the single biggest lever for Tabby.**

**How to apply to our engine (concrete):**
1. **Checkpoint at the points where the next request will branch,** not at a fixed interval. A DN snapshot is ~150 MiB total (~37 MiB per device on 4 devices, half that in f16). Take snapshots at:
   - (a) the end of the system prompt + tool list, shared by all sessions of an agent;
   - (b) the end of every assistant turn, just after `<|im_end|>\n`, where the next tool_response or user turn starts;
   - (c) optionally every 2–4K tokens during a long prefill, so a mid-prompt edit can resume.
2. **Each stage stores its own snapshots locally,** because layer state never leaves the device. The coordinator only keeps the radix tree of token-hash chains to checkpoint IDs. A request becomes `resume(ckptId, suffixTokens)`, broadcast to all stages. A stage that misses (evicted, or a new peer) reports it, and the coordinator falls back to the longest prefix that *all* stages have.
3. **Copy-on-write:** clone the snapshot into the session's live DN buffer with `copyBufferToBuffer`, a GPU-side copy that takes about 1 ms per 40 MB. KV for the prefix is shared read-only if paged; if not paged, copy it.
4. **Make the prompt stable.** Two current behaviors break this:
   - **`fitContext` truncates old turns,** which shifts everything. Use compaction or summary at fixed boundaries instead.
   - **Qwen templates that strip past `<think>` blocks** re-render history differently on every new user turn. Qwen 3.8 is trained with `preserve_thinking=true`, so keep reasoning in history, or drop it but snapshot *after* rendering with the dropped form.
   - Also never put timestamps or other volatile content in the system prompt.

## 4. SSD / disk caching

- **LLM in a Flash** ([Apple, arXiv 2312.11514](https://arxiv.org/abs/2312.11514)):
  - Weights stay on flash and only the needed rows are loaded, using activation-sparsity prediction, a sliding window of recently active neurons, and row-column bundling for larger contiguous reads.
  - Reported 4–5x (CPU) and 20–25x (GPU) over naive loading.
  - **Doesn't apply** to a dense Q4 model split across peers. Weights should stay resident.
- **FlexGen** ([arXiv 2303.06865](https://arxiv.org/abs/2303.06865)): throughput-oriented offload of weights, KV and activations across GPU/CPU/disk with a zig-zag block schedule and 4-bit KV. **Doesn't apply**; it is batch-throughput, not interactive.
- **LMCache** ([LMCache/LMCache](https://github.com/LMCache/LMCache)) and **vLLM KV offloading connectors:** chunked KV (256 tokens) keyed by prefix hash across GPU→CPU→disk/remote tiers, with CacheGen compression. There is recent hybrid-state recovery validation ([arXiv 2609.15030](https://arxiv.org/pdf/2609.15030)). **Applies conceptually:** chunk-hash keying, tiering and admission.
- **llama.cpp `--slot-save-path`:** whole-slot binary dump and restore; "nearly instant versus re-processing". **Applies:** the simplest possible v1 is a per-session dump of each stage's KV + DN.
- **Browser OPFS:**
  - `FileSystemFileHandle.createSyncAccessHandle()` works in dedicated workers only, with synchronous `read/write` into ArrayBuffers ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/createSyncAccessHandle)).
  - Reported about 100 MB in ~90 ms, roughly 1.1 GB/s, versus about 118 MB/s for IndexedDB ([Anirone](https://anirone.com/blog/general/opfs-vs-indexeddb-binary-storage)). Firefox numbers vary ([bench](https://github.com/tbrockman/firefox-opfs-simple-bench)).
  - Quota is per origin, typically a large fraction of free disk in Chromium. Call `navigator.storage.persist()` to avoid eviction.
  - **Estimate for one device at 1/4 of the layers:** a 32K session in f16 KV is about 537 MB, plus about 37 MB DN. Restore takes about 0.5–1 s of disk time plus GPU upload (`writeBuffer` of about 0.5 GB takes a few hundred ms). Re-prefilling 32K tokens across the swarm is minutes. **A 100x-class TTFT win for resuming sessions,** consistent with arXiv 2603.04428.
  - Layout: content-addressed 256-token KV chunks (SHA-256 via SubtleCrypto, or a fast xxhash in WASM) plus DN snapshots, under a manifest written last. That is Mesh-LLM's crash-safe pattern.
  - The GPU→disk path needs `mapAsync` readback into a staging buffer and then a worker write. Do it off the critical path, after the turn completes.
  - Weights already use the Cache API (`room.js`, `swarmllm-weights-v1`). Moving them to OPFS is optional, since load time is dominated by network the first time.

## 5. Tool calling for the Qwen3 / 3.5 / 3.8 family

- **Qwen3 (2025) original format, Hermes-style JSON** ([Qwen docs](https://qwen.readthedocs.io/en/latest/framework/function_call.html)):
  - System block: `# Tools\n\nYou may call one or more functions...\n<tools>\n{json schema per line}\n</tools>`.
  - Assistant emits `<tool_call>\n{"name": ..., "arguments": {...}}\n</tool_call>`.
  - Results come back in a user turn: `<|im_start|>user\n<tool_response>\n...\n</tool_response><|im_end|>`.
- **Qwen3-Coder / Qwen3.5 / 3.6 / 3.8 XML format.** This is what Qwen 3.8 is trained on (parser `qwen3_xml`, formerly `qwen3_coder`):
  ```
  <|im_start|>system
  # Tools

  You have access to the following functions:

  <tools>
  {"type":"function","function":{"name":...,"parameters":{...}}}
  </tools>

  If you choose to call a function ONLY reply in the following format with NO suffix:

  <tool_call>
  <function=example_function_name>
  <parameter=example_parameter_1>
  value_1
  </parameter>
  </function>
  </tool_call>
  ...(user system prompt appended)<|im_end|>
  ```
  - Assistant turns: `<think>\n...\n</think>\n\n` + optional text + one or more `<tool_call>` blocks, then `<|im_end|>`.
  - Tool results: consecutive `tool` messages are merged into **one** user turn, each wrapped in `\n<tool_response>\n...\n</tool_response>`.
  - Non-string parameter values are JSON-serialized inside `<parameter>`.
  - Generation prompt: `<|im_start|>assistant\n<think>\n`, or with thinking off, `<think>\n\n</think>\n\n`.
  - Qwen 3.8 is trained with **preserve_thinking=true** ("always-closed think blocks even when empty").
  - Sources: [Qwen3.8-27B template discussion](https://huggingface.co/Qwen/Qwen3.8-27B/discussions/68), [fixed templates](https://huggingface.co/froggeric/Qwen-Fixed-Chat-Templates), [Qwen3.5 format discussion](https://huggingface.co/Qwen/Qwen3.5-35B-A3B/discussions/4), and a reference template I downloaded from [allanchan339 fix repo](https://github.com/allanchan339/vLLM-Qwen3-3.5-3.6-chat-template-fix). The exact wording of the official 3.8 system instruction could not be fetched (HF is blocked here). Copy it verbatim from the model's `tokenizer_config.json` / `chat_template.jinja` rather than from this report.
- **Known failure modes:**
  - The model sometimes drifts from its own format ([ollama #16383](https://github.com/ollama/ollama/issues/16383)).
  - It emits a tool call inside an unclosed `<think>`.
  - A high reasoning_effort default in the official 3.8 template causes runaway thinking ([QwenLM/Qwen3.8 #217](https://github.com/QwenLM/Qwen3.8/issues/217)).
  - **Mitigation:** a tolerant streaming parser that auto-closes `</think>` before `<tool_call>` and accepts a missing `</parameter>` at `</function>`.
- **Cheap in-browser constrained decoding:**
  1. **Lazy / trigger-based grammar** (llama.cpp and XGrammar-2 style, [arXiv 2601.04426](https://arxiv.org/pdf/2601.04426)). Decode freely, but once `<tool_call>` is sampled, switch to a tiny state machine:
     - `<function=` → allowed names only (a token trie over the names from `<tools>`);
     - `>\n<parameter=` → allowed param names for that function, required ones first;
     - values stay free text until `\n</parameter>`.

     The mask is applied only on the last stage's logits and only inside tool calls, with an O(vocab) bitmask built once per state. That is about 1 ms in JS for 248K vocab, or better, a precomputed bitset per trie node.
  2. **MTP and speculation compatibility:** reject drafts that violate the mask, or mask draft logits too.
  3. Full JSON-schema constraint for object-valued params: **XGrammar compiled to WASM** is the one used by WebLLM ([MLC blog](https://blog.mlc.ai/2024/11/22/achieving-efficient-flexible-portable-structured-generation-with-xgrammar)). It is optional; start with the trie.

## 6. WebGPU long-context attention kernels

- **ONNX Runtime WebGPU:**
  - Flash attention for prefill ([PR #22932](https://github.com/microsoft/onnxruntime/pull/22932)).
  - Flash decoding for generation, QKT → split-VX → reduce ([PR #23808](https://github.com/microsoft/onnxruntime/pull/23808)).
  - Intel subgroup prefill FA ([PR #32702](https://github.com/microsoft/onnxruntime/pull/32702)): K/V stored transposed `[head_vec][kv_step]` in shared memory to avoid bank conflicts; V loaded *after* QK^T so its latency hides behind softmax; subgroup shuffles with a host-chosen kv_step of 8 or 16; +12–20% at 2–4K.
  - GPU-side metadata for paged attention with no readbacks ([PR #32277](https://github.com/microsoft/onnxruntime/pull/32277)).
- **Applies:**
  - Our decode `attn_flash` already has the split-K and GQA-sharing structure. Next steps:
    - `subgroupAdd`/`subgroupMax` for the per-split reductions where `subgroups` is available, keeping the bit-identical workgroup path as the fallback;
    - `shader-f16` vec4 loads;
    - fold K dequant (q8) into the load.
  - Prefill/verify at long context needs a tiled flash-attention (Q tile x K tile in workgroup memory, online softmax). The current `attn_*_mc` path depends on the ≤2048-position workgroup softmax, so **prefill at 32K is the next bottleneck after decode.**
  - Prefill cost is dominated by the 48 DN layers and the FFN matmuls, not attention, until roughly 16K+ tokens.

## Ranked recommendations

1. **Hybrid prefix cache with DeltaNet snapshots at turn boundaries (per stage, radix tree on the coordinator).** This is the biggest win for multi-turn agents (95.7% of input tokens reusable). Snapshot after system+tools and after every assistant `<|im_end|>`. Copy-on-write into the live slot. `resume(ckptId, suffix)` protocol. Fall back to the longest prefix all stages share. Tail-Replay only as an approximate fallback.
2. **Stable prompt rendering.** Stop front-truncating in `fitContext`, keep `preserve_thinking`, and keep volatile text out of the system prompt. Without this, #1 misses.
3. **f16 KV + split-K flash decode everywhere (already in the working tree), then q8_0 KV for 32K–64K.** Avoid q4 K, because Qwen's damage concentrates in long documents and tool calls. Validate with KL on long-document and tool prompts.
4. **Qwen 3.8 XML tool-call format + tolerant streaming parser + trigger-based name/param trie mask on the last stage.** XGrammar-WASM later for JSON-valued params.
5. **Suffix n-gram proposer chained after MTP.** Longest exact match 3–64 tokens over the whole session history, not a 4096-token window. Mesh-LLM measured +156% over MTP-only on coding-copy workloads, where agents re-emit files and tool outputs.
6. **OPFS L3 session store** (content-addressed KV chunks + DN snapshot + manifest, written after the turn from a worker with `createSyncAccessHandle`). Restoring a 32K session is about 1 s versus minutes of re-prefill. Enables cross-session and tab-reload resume.
7. **Concurrent sessions via a paged KV block table + multi-session batched columns.** With D pipeline stages, keep up to D sessions in flight so every device is busy (Petals/exo/prima pipeline fill). Shared system-prompt pages are shared for free.
8. **Pipelined verify windows + Petals-style replay for fault tolerance.** Keep 2–4 speculative windows in flight across the WebRTC chain with epoch invalidation, and snapshot DN before each window for rollback. Log per-stage inputs, or rely on OPFS snapshots, so a peer that drops can be rebuilt without restarting the session.

Not recommended: SSD weight streaming (Edge0, fp4brain, LLM in a Flash, FlexGen) for this dense model; tensor parallelism (distributed-llama) over WebRTC; q4 KV by default.
