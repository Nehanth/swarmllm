# Next kernel and engine levers: dense 27B and the MoE path (September 2026)

Written 2026-09-26 from reading `origin/tabby-new-idea` and from outside sources. Nothing in this document was run on a GPU; the GB10 was busy. Numbers marked **[M]** come from the repo's own measurements (bench-log.md, research/decode-overhead-and-wire.md, kernel-plan-3.md, deltanet-prefill-research.md). Numbers marked **[E]** are my estimates. This document picks up where `research/kernels-2026-09.md` stopped and does not repeat its items. Where an item overlaps with that document, it says so.

"Exact" means the change keeps today's bits for every column of every pass, so the current goldens (`tests/test_mtp.js`, `test_batch*`, `test_twins.js`, `engine_synth`) still pass unchanged. "Flag" means the change reorders a floating-point reduction. Such changes must stay behind an off-by-default switch, and every device in a room must pick the same setting, because the setting is part of the protocol.

## 1. Where a token's time goes today

### Dense 27B, plain decode (GB10, Deno/wgpu, pos ≈ 8, 108 ms/token [M])

| Bucket | ms | Notes |
|---|---|---|
| All GEMVs (~15 GB of weights) | 80 | Close to the 184 GB/s WebGPU streaming probe, but only 67% of the 273 GB/s DRAM peak. Per shape [M]: gate/up 143 GB/s, 5120² 166 GB/s, LM head 207–211 GB/s. Small shapes (512–1024×5120) sit at a ~0.05 ms launch floor. |
| Deno `mapAsync` poll sleep | 11.6 | Deno only. Chrome polls Dawn every 1–2 ms. |
| CPU encode of 898 dispatches / 145 passes | 4.1 | On the critical path because nothing is encoded ahead. |
| `dn_delta` (48 WGs × 128 threads) | 5.2 → ~3.3 | Register-resident version is on the branch. There is one serial 128-step FMA chain per thread and only 48 workgroups. |
| rmsnorm (129 dispatches) | 3.0 | About 23 µs each, one workgroup. |
| DeltaNet and attention glue | ~5.7 | Partly fused on the branch (`attn_glue`, `dn_delta_gn`). |
| Attention | 0 → 8.7 at pos 500 | Flash-decoding plus f16 KV is on the branch, not yet timed. |

**Bytes, not kernels, set the floor, and 8.2 of the 15 GB are Q8_0.** In this file `ffn_down` (64 × 94.7 MB = 6.1 GB), `ssm_out` (48 × 33 MB = 1.6 GB) and `attn_output` (16 × 33 MB = 0.5 GB) are Q8_0 [E, from the shapes]. A pure-Q4_0 requantize (`llama-quantize --pure`) would stream about 10.5 GB per token instead of 15, so decode would be about 30% faster. That is a different model file, not a kernel change, so it breaks every golden. It is listed only so nobody expects kernels to deliver that 30%.

### Dense 27B, speculative K=3 (16 tok/s ≈ 215 ms/step for ~3.3–3.55 tokens [M])

The step is: 3 drafts (each an MTP block of ~0.2 GB plus the Q8 LM head of ~1.27 GB ≈ 6.9 ms, plus a sync), a 4-column trunk pass (125–134 ms; its batched GEMVs cost 95–97 ms against 80 ms for one column), a hidden-state readback, `headBatch` (4-column LM head plus a 4 MB readback), and then `a` sequential MTP refill passes. On Deno that is K+2 = 5 sync points × 11.6 ms. Putting the whole step in one submit brings it to 162 ms [M]. The draft LM head accounts for about 21 ms of every step.

### MoE 35B-A3B (Q4_0, estimated from the shapes; not run anywhere)

Bytes per token [E]:
- Routed experts: 40 × 8 × 3 × 512 × 2048 × 0.5625 B = 566 MB.
- Shared experts: 71 MB.
- DeltaNet projections: 30 × ~19 MB.
- Attention projections: 10 × ~15 MB.
- F32 routers: 84 MB.
- LM head: 248320 × 2048, about 540 MB at Q8.

That totals about 2.0 GB, or **11 ms at 184 GB/s (~90 tok/s ceiling)**, and the LM head alone is 27% of it.

Dispatches per token are about 40 × (9 FFN + 8–12 mixer) ≈ 750–850, nearly as many as the dense model. So **the MoE path will be bound by dispatch count and small-kernel efficiency, not by bandwidth.** An outside CUDA write-up saw the same thing: Qwen3.6-35B-A3B went from 9 to 40 tok/s on a 4090 purely by batching the expert launches and removing host round trips ([zolotukhin.ai](https://zolotukhin.ai/blog/2026-06-11-cuda-llm-decode-optimization-batched-moe-kernel-fusion/)). This engine already reads the routing on the GPU, so the host round trip is gone. What remains is kernel quality and launch count.

## 2. Concrete inefficiencies found in the code

1. **The coop GEMV issues one 4-byte weight load per thread per row per iteration** (`coop.js` `q4_row`/`q8_row`, `wIdx = row0*rowWords + b*4 + qt`). With 4 rows, that is 16 B in flight per thread per trip. Marlin, Machete and llama.cpp's `mmvq` all issue 16-byte weight loads per thread, with several loads in flight, and dequantize in registers ([Marlin](https://github.com/IST-DASLab/marlin), [Machete](https://neuralmagic.com/blog/introducing-machete-a-mixed-input-gemm-kernel-optimized-for-nvidia-hopper-gpus/), [LlamaWeb, arXiv 2605.20706](https://arxiv.org/html/2605.20706v1)). kernel-plan-3 already names "more bytes in flight per thread" as the #1 decode lever, but it has not been built, and it was specified in a way that is not exact. §3 gives an exact form.
2. **Each small GEMV gets its own dispatch.** A DeltaNet layer launches `mvQKV`, `mvZ`, `mvBeta` and `mvAlpha` separately, all with dIn = 5120. Beta and alpha are 48 rows each, which is 12 workgroups at the launch floor. Attention layers launch Q, K and V separately, and K and V are 1024 rows each.
3. **`specStep` reads the verify hiddens back to the CPU, then writes them back for `headBatch`** (`verifyN` → `embedRunBatch` → `_runBatchAndRead` → `headBatch(hs)`). In solo mode that is one extra sync plus a copy through the CPU for no reason. The CPU only needs them for `setHidden`, and a GPU copy (`_adoptHidden`) does the same job.
4. **The MTP refill runs `a` separate single-column MTP passes after every accept** (`for j in 1..a: mtpRun(...)`). Each pass streams the ~0.2 GB MTP block again. `_mtpFillBatch` already does exactly this as one batched pass during prefill.
5. **The MoE expert kernels (`moe.js`) are well below the dense kernels' quality:**
   - `moe_gu`: dIn = 2048, so nb = 64, and each of the 64 threads handles exactly one block per row. Rows are processed one at a time, each followed by a full 7-level tree with barriers, so there are about 28 barriers per workgroup for 4 rows.
   - `x` is read as 32 scalar loads per block instead of vec4 loads, and there is no `unpack4xU8`.
   - `moe_dn`: dIn = 512, so nb = 16, and **only 16 of the 64 threads do any work.**
6. **`moe_router` runs its softmax sum, its normalization and all 8 top-k scans on thread 0**, about 2,300 serial shared-memory operations per layer. At about 20 cycles each that is roughly 30 µs per layer, or about 1.2 ms per token [E]. The router GEMV (F32, 256×2048) and the shared-expert gate GEMV (F32, 1×2048) are two more dispatches that read the same `xn`.
7. **`moe_combine` is a separate pass that re-reads `y[K][dim]`.** The down kernel could fold the weighted sum into its own epilogue.
8. **The MoE verify and prefill passes run each (column, slot) pair on its own** (workgroup y = col*K + slot). An expert chosen by 3 of 4 verify columns is streamed 3 times. llama.cpp's `mul_mat_id` groups by expert (see §5).
9. **The single-workgroup `argmax` walks all 248,320 logits through one SM** (~970 serial elements per thread). A 2-pass design is already specified in kernel-plan-3 Part B. It only matters without `draftvocab`.
10. **`bench_breakdown.js` attributes time with stale skip lists** (decode-overhead §1.0). Nothing uses timestamp queries, even though `timestamp-query` has worked in compute passes since Chrome 121 ([release index](https://developer.chrome.com/blog/new-in-webgpu-145)) and wgpu supports it too.

**Suggested order:** D9 → D1 → D2 → D3 → D5 → D4 → D6. Everything through D6 is exact. D7, D8 and D10 are a separate "fast profile" flag for rooms where every device agrees to it. Taken together, the exact items (D1+D2+D3 on steps, D4+D5 on bytes and launches) point to **~21–24 tok/s spec and ~10–10.5 tok/s plain on Deno [E]**.

## 4. Ranked changes: MoE (Qwen3.6-35B-A3B)

MoE goldens have not yet been frozen on real hardware (tabby-kernel.md: "timing on real hardware: not done"). **The cheapest moment to change the MoE kernels' reduction orders is before those goldens exist.** The invariants that have to hold are batched == single and spec == plain, and every item below keeps them by construction, because each (column, slot) pair runs the same arithmetic in every pass width.

Architecture facts that matter for the kernels (research/moe-2026-09.md; official config): hidden size 2048, 40 layers (layers 3, 7, …, 39 are full attention and the other 30 are Gated DeltaNet), **256 experts, top-8**, expert FFN 512, **one shared expert** (FFN 512) scaled by a scalar `sigmoid(w_sg·x)`, softmax over all 256 experts then renormalization over the chosen 8, no routed scale, and every layer is MoE. The MTP block is itself a MoE layer.

Verify this with D9 before believing either number.

## 5. State of the art, briefly, and what transfers

- **llama.cpp.** The `GATED_DELTA_NET` op ([PR #19504](https://github.com/ggml-org/llama.cpp/pull/19504)) splits the columns of the state across warps and the rows of each column across lanes, keeps the state in registers, and reduces with warp shuffles; the Vulkan shader uses `subgroupClusteredAdd` with a shared-memory fallback. **This is D7.** The Vulkan GDN decode path still has problems: Qwen3.6-35B-A3B decode collapses to ~4 tok/s on RDNA4 ([#26795](https://github.com/ggml-org/llama.cpp/issues/26795)), and Qwen3.5-27B produces garbage at batch 512 ([#27237](https://github.com/ggml-org/llama.cpp/issues/27237)). That fits this engine already beating llama.cpp CUDA on the GB10 (9.0 vs 8.0 tok/s [M]). The CUDA backend's decode gains came mostly from fusions (GEMV+gate, rmsnorm+mul, topk-moe, weighted expert reduction; +37–42% on MoE, [am17an](https://am17an.bearblog.dev/new-post/), [PR #25952](https://github.com/ggml-org/llama.cpp/pull/25952)). **Those map to D5, D6, M2 and M4.**
- **llama.cpp WebGPU (LlamaWeb, [arXiv 2605.20706](https://arxiv.org/html/2605.20706v1)).** Decode GEMV holds x in registers, uses a cooperative row reduction (subgroup when available, shared memory otherwise), and dequantizes in registers. It is about 50% behind native Metal on Apple and at parity with SYCL on Intel Arc. It supports `MUL_MAT_ID`, and the subgroup-matrix path is Dawn-native only. Nothing there beats this engine's GEMV structure; the gap is load width (D4) and fusion.
- **ORT-web / Transformers.js.** MatMulNBits has DP4A and subgroup-matrix paths ([PR #23729](https://github.com/microsoft/onnxruntime/pull/23729), [AMD wave64 #32796](https://github.com/microsoft/onnxruntime/pull/32796)). Subgroup-matrix helps prefill, not GEMV decode. It is still `chromium-experimental-subgroup-matrix`, behind a flag.
- **MLC/WebLLM** keeps up to ~80% of native MLC decode ([WebLLM paper](https://arxiv.org/html/2412.15803v2)). It has no Gated DeltaNet or Qwen3.5-MoE-specific kernels that I could find.
- **fla** ([flash-linear-attention](https://github.com/fla-org/flash-linear-attention)): the `fused_recurrent_gated_delta_rule` decode kernel keeps an fp32 state, folds the decay into the kv reduction and touches the state twice. That matches `dn_delta` today. FlashQLA ([Qwen blog](https://qwen.ai/blog?id=flashqla)) targets chunked prefill (2–3× over fla), which is not relevant to decode.
- **Marlin / Machete** (low-bit GEMM/GEMV): pre-shuffled weight layouts so each thread issues 16 B loads and dequantizes in registers, with lop3 tricks. The layout idea transfers (D4); a weight re-layout at load would also be exact, since it only changes which thread loads which bytes, provided the logical accumulation order is kept.
- **MoE decode kernels**: grouped by expert with GPU-resident routing ([zolotukhin.ai](https://zolotukhin.ai/blog/2026-06-11-cuda-llm-decode-optimization-batched-moe-kernel-fusion/)); speculative verify cost is set by the expert union ([EcoSpec](https://arxiv.org/abs/2607.12696), [adaptive verification](https://arxiv.org/html/2605.00342v1)). These become M5 and M9.
- **WebGPU in Chrome, 2026:** subgroups (134; `subgroup_id` 144; `subgroup_uniformity` 145), `shader-f16` (120), DP4a (123), compute timestamp queries (121), faster `writeBuffer` (144), experimental worker `mapSync` (145, worth testing against the per-step sync cost); subgroup matrix still experimental ([134](https://developer.chrome.com/blog/new-in-webgpu-134), [144](https://developer.chrome.com/blog/new-in-webgpu-144?hl=en), [145](https://developer.chrome.com/blog/new-in-webgpu-145)).
  - Deno/wgpu on the GB10 exposes no subgroups, so anything that relies on subgroups needs the shared-memory path, and its reduction order then differs between runtimes. **That is one more reason D7 and D8 must be flagged, never silently autotuned.**

## 6. Measurement protocol for every item

1. **Correctness first.** The golden suite must pass byte-for-byte (`tests/test_mtp.js`, `test_twins.js`, `tests/e2e/engine_synth.mjs`, plus `--moe`, `moe_kernels.mjs`, `moe_synth.mjs`, `fusion_synth.mjs`). For flagged items: tolerance vs float64 plus greedy-token agreement on the standard prompts (`hello`, `meaning`, `japan`).
2. **Kernel time.** Use D9's timestamp queries per pass (warm clocks: the GB10 governor moves the probe between 82 and 118 GB/s across processes [M]). Report kernels as a fraction of an in-process streaming probe, and add a 16 B/thread probe next to today's.
3. **End to end.** `MODEL=q38 deno … benchmarks/bench.js` (plain and spec lines), then the room on Chrome with the `japan` prompt, second answer, a row in bench-log.md. Report Deno and Chrome separately, because the sync-cost items (D1, D3) are worth 3–10× more on Deno.
4. **Dispatch cost.** Before ranking M6 and D5 by milliseconds, measure the in-stream per-dispatch cost with timestamps on Vulkan (Chrome), Deno and Metal. The −128 `add_res` removal measured neutral on the GB10 [M], so the isolated 0.05 ms launch floor may overstate it.
