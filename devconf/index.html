swarmLLMPart 3 · Under the hood

The tech stack: a web page, all the way down to your GPU.

kernela small program that runs on the GPU and does one piece of math, like a matrix multiply. Also called a shader
"People always ask: what inference engine is this? Is it llama.cpp? Is it PyTorch? It's neither. It's its own engine. Here's the whole stack, top to bottom. At the top, a link in a browser tab. Nothing to install. Under that, plain JavaScript. About six thousand lines. It turns text into tokens, picks the next token, and runs the room. Under that is WebGPU, which is how a web page reaches your graphics chip. Under that are my kernels. Forty-three of them. A kernel is just a small program that runs on the GPU and does one piece of math, like a matrix multiply. And at the bottom, your actual GPU. Apple, NVIDIA, AMD, Qualcomm. Same code on all of them." [→ the two layers I wrote light up] "Two of these layers I wrote from scratch. The JavaScript engine and all forty-three kernels. That's more work, but it means I get to shape every kernel around exactly one model family." [→ weights stream in from the left] "The weights never pile up in normal memory. Each device downloads only its own layers and they go straight onto the GPU. The browser caches them, so the second load comes off disk." [→ three versions race on the kernel layer] "And every device tunes itself. While it loads, it tries a few versions of the slowest kernels and keeps whichever is fastest on that chip. A phone and a desktop end up picking different ones." IF ASKED how this compares to PyTorch, llama.cpp or WebLLM: there's a backup slide, "four ways to run an LLM".
swarmLLMPart 3 · Under the hood

One engine, very different GPUs.

example room · the layers are dealt by memory first, then speed
"And the devices in a room are nothing alike. A MacBook with an Apple GPU. A gaming PC with an NVIDIA card. An Android phone. An iPhone. Completely different chips, completely different drivers. And it's the same code running on all four." [→] "So every device checks itself when it joins. First it runs the kernels against known answers, because GPU drivers don't always agree with each other on the math. Then it tunes itself for that chip." [→] "Then the room deals the layers by what each device can actually do. Memory first, then speed. The MacBook takes forty-four. The PC takes sixteen. The phones take two each. So a slow phone never ends up holding half the model."
swarmLLMPart 3 · Under the hood

One week: 2.5 → 10.7 tokens a second. How?

tok/stokens per second. 10 tok/s is about 7 words a second, faster than most people read
"So what did all that buy? This is launch day. Same MacBook, same iPhone as the demo. Two and a half tokens a second. Watch the text. That's not an assistant. That's a telegraph." [→ 6.7] "Step one. Remember, it's one pass per token, and every pass reads the whole model out of memory. So writing the answer isn't waiting on math. It's waiting on memory. And my first kernels read memory the slow way: thousands of GPU threads, each grabbing from a different place. So I rewrote them so the threads sweep through memory together, in one clean pass. Same math, same answer. Six point seven. Watch the text speed up." [→ 10.7] "Step two is guessing ahead. The model comes with a tiny helper that guesses the next few tokens. The big model checks all of them in a single pass. Every right guess is a free token. The real name is speculative decoding. Ten point seven. One week after launch." [→ same output] "And one rule through all of it. A speed-up only counts if the answer stays exactly the same. Byte for byte. The test suite checks it on every change. Because if the output changes, you didn't make the model faster. You made a different model."

The problem is latency, not bandwidth. Every token visits every device, in order, and each hop adds about 15 ms of pure waiting.

More devices means a bigger model fits. It doesn't mean a faster answer. Yet.

help wantedkeep every device busy instead of waiting for the token to come back around. Overlapping laps is roadmap #9.
latencyhow long one message takes to arrivebandwidthhow much you can send per second
"Now the bad news, and the open challenge of this whole project. It's hard to scale. Layer two can't start until layer one is done. Inference is a chain. This is where that bites. Picture passing a note down a row of seats. The note is tiny. What takes time is every handoff. Longer row, slower note. And a bigger pipe does nothing for you. Same thing here. Every token visits every device, in order, and every hop costs about fifteen milliseconds of pure waiting. So I measured it. Same machine every time, more and more devices." [the ring cycles through these by itself] "One device, no network at all: about sixteen tokens a second. Three devices, about ten. Sixteen devices, about four." [→] "So let me be really clear about what this is. More devices gets you a bigger model. It does not get you a faster one. But the alternative isn't 'faster'. The alternative is 'doesn't run at all'. And honestly, this is the open challenge of the whole project. How do you scale this to more people without every new device slowing everyone down? Right now most devices sit idle, waiting for the token to come back around. I have ideas, like overlapping the laps so nobody waits. If you do networking for a living, this one has your name on it."

swarmLLMBackup · limits

What it is, and what it isn't yet.

what you get

  • A model none of your devices can run alone, running on all of them
  • No account, no API key, no server keeping your chats
  • The same answers. Splitting changes where the math runs, not the math
  • Nothing to install. Any device with a modern browser

what it isn't

  • Not faster than one big GPU. It's for when you don't have one
  • Not private between strangers. Each device sees the activations passing through it
  • Nothing checks that a device did the work honestly. Open problem
  • Short context. 2,048 tokens, single turn
"What it is: a model none of your devices can run alone, no account or API key, identical output, nothing to install. What it isn't. It's not faster than one big GPU. It's not private between strangers, every device sees the activations passing through it. Nothing verifies a peer's work yet. And the context is short. That's why today it's for your own devices and people you trust."

swarmLLMBackup · trust

Trust: today it's your own devices.

how it works today

  • Your words stay on the host. Peers only receive the numeric thought
  • WebRTC encrypts every hop in transit
  • The host can show the chat to everyone, only itself, or only the asker

open problems

  • The thought isn't encryption. Research shows text can sometimes be recovered from it
  • A peer could return garbage. The math is deterministic, so a slice can be re-run and compared
  • Proving it to someone else is confidential-compute territory
"Today the answer is simple: your own devices, people you trust. The prompt never leaves the host as text, but the numbers passing through peers aren't encryption. The one thing in my favour: the math is deterministic. So you can re-run the same slice on a second peer and compare. That's the cheap first step. Beyond that it's an open research area and I'd love help."
swarmLLMBackup · speculative decoding

Speculative decoding: free tokens when right, nothing lost when wrong.

one pass, several tokens

  • The model ships with a tiny draft head that proposes the next 3 to 7 tokens
  • The big model verifies all of them in one pass
  • It keeps the guesses it agrees with and throws away the rest

why the answer is identical

  • The big model always has the final say on every token
  • A test runs both paths and compares the output byte for byte
  • Across a slow network it matters most: one round trip, several tokens
"The model ships with a tiny draft head. It proposes a few words, the big model verifies them in one lap, keeps the ones it agrees with, discards the rest. The big model always has the final say, so the output is identical. There's a test that runs both paths and compares byte for byte."

Two phases: read the prompt, then write the answer.

prefillreading the prompt, all of it in one passdecodewriting the answer, one pass per token. The part you wait for
"If someone asks about prompt processing, or time to first token. The model runs in two phases. Phase one is prefill. That's the model reading your prompt. Every prompt token goes through the model side by side, in a single pass. It's one big batch of matrix multiplies, which is exactly what GPUs are good at. So it's quick. And the model keeps what it learned about the prompt in memory, so it never has to read it again." [→ decode] "Phase two is decode. That's the model writing the answer. Now only the newest token goes in. One token per pass. It comes out, loops back around, and becomes the next input. And every one of those passes reads the entire model out of memory again. Watch the counter. Decode is the part you sit and wait for. So when I say tokens per second later, I mean decode."

Four ways to run an LLM. This engine is its own.

No framework underneath

Most AI apps sit on PyTorch or llama.cpp, or let a compiler write their GPU code. This one brings its own 43 kernels.

Weights go straight to the GPU

Each device downloads only its own layers, and the browser caches them.

It tunes itself on your device

Each device tries a few versions of the slowest kernels and keeps the fastest.

kernela small program that runs on the GPU and does one piece of math, like a matrix multiply. Also called a shader
"People always ask: what inference engine is this? Is it llama.cpp? Is it PyTorch? It's neither. So here are the usual ways to run an LLM, left to right. PyTorch. A Python script, talking to NVIDIA's libraries, on NVIDIA GPUs. That's the datacenter. llama.cpp and Ollama. A native app you install, with a hand-made set of GPU code for every GPU brand. WebLLM. A browser tab, on WebGPU, and its GPU code is generated by a compiler. And mine, on the right. Also a browser tab, also WebGPU, which is how a web page talks to your graphics chip. But the GPU code is its own. Forty-three kernels. A kernel is just a small program that runs on the GPU and does one piece of math, like a matrix multiply. About six thousand lines of JavaScript on top. And it runs on any GPU. Apple, NVIDIA, AMD, Qualcomm. Phones included. And look at the bottom row. Can it split one model across devices? PyTorch can, in a datacenter. llama.cpp can, if you set it up by hand. WebLLM can't. This one does it with a room code." [→] "If you've seen WebLLM, that's the best-known way to run an LLM in a browser. It lets a compiler generate its GPU code. I went the other way and wrote all forty-three myself. It's more work, but I get to shape every one of them around exactly one model family." [→] "The weights never pile up in normal memory. Each device downloads only its own layers and they go straight onto the GPU. The browser caches them, so the second time you load, it comes off disk." [→] "And every device tunes itself. While it loads, it tries a few versions of the slowest kernels and keeps whichever is fastest on that chip. A phone and a desktop end up picking different ones." The 43 kernels, by family.

Matrix multiplies

where almost all the time goes

  • matvec · f32, Q8_0, Q4_0
  • cooperative GEMV: threads sweep rows together
  • fused gate + up, twin and batched variants
  • row-stationary Q4_0 GEMM for prefill (16 tokens at once)

Full attention

the classic transformer layers

  • per-head RMS norm on Q and K
  • RoPE, and partial NeoX RoPE
  • attention scores · softmax · output
  • KV cache, sigmoid output gate

Linear attention

Gated DeltaNet: Qwen 3.5 / 3.8 is a hybrid

  • causal conv (K=4) + SiLU with rolling state
  • per-head gates: sigmoid beta, decay
  • per-head L2 norm
  • gated delta rule recurrence · gated norm

Glue

small, but they run on every layer

  • RMS norm
  • SiLU gate (SwiGLU)
  • residual add
  • argmax on the GPU

All WGSL, all in engine/wgsl/. Every device self-tests them against known answers at load, then times a few shapes of the matrix multiplies and keeps the fastest.

"Forty-three kernels, four families. Matrix multiplies are where almost all the time goes, so that's where the work went: four-bit and eight-bit versions, the cooperative version where a group of threads sweeps rows together, and a separate one for prefill that handles sixteen tokens at once. Full attention is the classic transformer part: norms on Q and K, RoPE, scores, softmax, the KV cache. Linear attention is the newer part. Qwen 3.5 and 3.8 are hybrids, so some layers use Gated DeltaNet instead of attention. That needed its own kernels: a small causal convolution, the gates, and the delta rule recurrence. And the glue: RMS norm, the SiLU gate, residual add, and argmax on the GPU so the logits never leave it."

Q. Why write your own kernels?

  • The goal was a link, not an install. That means the browser, and the browser means WebGPU.
  • Existing browser engines assume one device holds the whole model. Splitting by layer needs control over every layer.
  • Shaping them around one model family paid off: 2.2× faster than my first version, with identical output.
"Short version: I wanted anyone to join with a link, so it had to be the browser, so it had to be WebGPU. The engines that already run in a browser assume one device holds the whole model. I needed to load any slice of layers on any device, hand the hidden state off, and keep the output identical. Owning the kernels made all three possible. Speed was a bonus, not the reason. And to be clear, the two point two times is against my own first kernels. I haven't raced WebLLM."
swarmLLMFAQ · 02 of 12

Q. Why WebRTC? Why not a server in the middle?

  • It's the only way two browsers can talk directly.
  • Direct means no server ever sees your prompt, and I don't pay for anyone's traffic.
  • It's encrypted by default. A relay fallback for strict networks is roadmap #1.
"WebRTC is how two browsers connect directly. It's what video calls use. If I put a server in the middle, that server sees every hidden state and I pay for the bandwidth. With WebRTC the only server is the matchmaker, and it's done after the handshake. The cost is that some strict networks block it. That's roadmap item one, a relay fallback."
swarmLLMFAQ · 03 of 12

Q. Why a browser at all?

  • Because “install this” loses most people, and phones can't install a Python stack.
  • WebGPU shipped in Chrome in 2023 and Safari in 2025, so almost every device has it.
  • One codebase runs on Apple, NVIDIA, AMD and Qualcomm GPUs.
"The honest answer is reach. A phone is never going to pip install anything. A link works on all of them. And WebGPU is finally everywhere, so the browser can reach the GPU properly."

Q. Why not just run a smaller model?

  • If an 8B model is good enough, run that on one device. It'll be faster.
  • This is for when you want the bigger model's quality and don't want a datacenter.
  • Bigger models need more memory than any one of your devices has. Together they have it.
"Totally fair. If a small model does the job, use it. This is for the case where you want a twenty-seven B model and you don't own a machine that fits it."

Q. Will it run on my phone?

  • It needs WebGPU: a recent Chrome on Android, or Safari on iOS 26.
  • A phone that can spare about half a gigabyte can hold a couple of layers.
  • Phones are the slowest link, so the room gives them the fewest layers.
"If your browser has WebGPU, yes. A phone won't carry much, a couple of layers, but it's really in the pipeline. Try it and tell me what breaks, that's the most useful thing you can do."

Q. How fast is it, honestly?

  • ~10.7 tok/s on a MacBook Pro plus an iPhone. ~16 on one device with no network.
  • More devices make it slower, not faster: about 10 with three, about 4 with sixteen (emulated).
  • One big GPU beats it easily. The point is that it runs at all on what you own.
"About ten tokens a second on a laptop and a phone. It gets slower as you add devices, because every token visits every device. It will never beat one big GPU. It's for when you don't have one."
swarmLLMFAQ · 07 of 12

Q. What happens when a device leaves?

  • The room notices in under two seconds and stops that answer.
  • It re-deals the missing layers to the devices still there. The next prompt works.
  • This is experimental. Spare copies, so an answer survives a drop-out, are roadmap #3.
"Today the current answer stops, the layers get re-dealt, and the next prompt works without anyone refreshing. That part is experimental. Keeping the same answer going through a drop-out needs spare copies of each slice, and that's on the roadmap."
swarmLLMFAQ · 08 of 12

Q. Is it private?

  • The matchmaker never sees your prompt. Devices talk directly and encrypted.
  • But every device in the room sees the numbers passing through it. That's not encryption.
  • So today: your own devices, and people you trust.
"Private from servers, yes. Private from the other devices in your room, no. They see the hidden states going through them. So use it with your own devices and people you trust. Doing better than that is an open research area."

Q. Which models does it run?

  • Two engines: a dense one for small Qwen 3 models, and a hybrid one for Qwen 3.5 / 3.8.
  • The talk uses Qwen 3.8 27B at 4 bits: 15 GB, open weights.
  • A new model family means new kernels. That's a good first big contribution.
"Right now it's Qwen. A small dense engine for testing, and the hybrid engine for the twenty-seven B. The kernels are shaped around that family, so adding another family is real work, but it's well-defined work."
